Bot Factory — Guía de Despliegue v1.1

Bot Factory se instala en tres servidores: su base de datos, un servidor de voz y un servidor de aplicación. Todo corre en Docker excepto la base de datos. Si sabe copiar archivos y pegar comandos, puede hacerlo.

Tiempo estimado: ~30 minutos incluyendo DNS y la preparación de SQL — la parte de Docker toma unos 5 · Basado en Docker

¿Ya tiene una versión anterior instalada? Vaya a Actualizar desde la v1.0.

⬇ Descargar los archivos de despliegue  (docker-compose + plantillas .env)

Los tres servidores

Configúrelos en este orden: base de datos → voz → aplicación.

Servidor 1Base de datos

Windows + SQL Server. Ya lo tienen — solo apuntamos la aplicación hacia él.

Servidor 2Voz

Linux + Docker, dedicado al audio en vivo. Necesita un dominio y puertos abiertos.

Servidor 3Aplicación

Linux + Docker con todo lo demás: sitio web, API, agente de voz y servicios auxiliares.

Antes de empezar

  • Los archivos de despliegue — descargue el zip de arriba. Trae una carpeta por servidor: deploy/livekit/ (Servidor 2) y deploy/bot_factory/ (Servidor 3).
  • Acceso al registro de imágenes — un usuario y contraseña que le entregamos, para descargar las imágenes. No necesita cuenta en la nube.
  • Dos nombres de dominio, uno para el Servidor 2 y otro para el Servidor 3, cada uno apuntando (registro DNS tipo A, sin proxy) a ese servidor.
  • Un certificado HTTPS y su llave para cada uno de esos dominios, en formato PEM (el archivo del certificado debe incluir la cadena completa). Copiará los dos archivos en una carpeta certs/ en cada servidor.
  • Docker en los Servidores 2 y 3 — verifique con docker --version. Si no está instalado: curl -fsSL https://get.docker.com | sudo sh.
  • Puertos abiertos — Servidor 2: 80, 443, 7881/tcp, 50000-50100/udp públicos + 7880/tcp desde el Servidor 3. Servidor 3: 80, 443 públicos; debe alcanzar el Servidor 1 (1433) y el Servidor 2 (7880).

1Servidor 1 — Base de datos (solo preparación)

  1. Active la Autenticación de SQL Server.
  2. Cree un inicio de sesión (por ejemplo botfactory) con una contraseña robusta. Otórguele dbcreator, o cree previamente una base de datos BotFactory vacía cuyo propietario sea ese inicio de sesión. (La aplicación crea sus tablas al arrancar por primera vez.)
  3. Asegúrese de que el puerto 1433 sea alcanzable desde el Servidor 3.
SQL Server 2025 o superior. La búsqueda usa el tipo nativo vector; en versiones anteriores falla la creación del esquema.

Anote la dirección, el usuario y la contraseña — los va a necesitar en el Servidor 3.

2Servidor 2 — Voz (LiveKit)

Copie deploy/livekit/ a este servidor y complete los valores en .env:

cd livekit
cp .env.example .env
nano .env
LIVEKIT_DOMAIN=voice.sudominio.com           # el dominio de este servidor
TLS_CERT=/etc/nginx/certs/fullchain.pem      # su certificado, copiado en ./certs
TLS_KEY=/etc/nginx/certs/privkey.pem
LIVEKIT_API_KEY=botfactory
LIVEKIT_API_SECRET=<paste output of:  openssl rand -hex 32>

Descargue e inicie los contenedores — estas imágenes son públicas, aquí no hace falta acceso al registro:

docker compose -f docker-compose.livekit.yml pull
docker compose -f docker-compose.livekit.yml up -d
curl https://voice.sudominio.com/

OK, con un certificado HTTPS válido.

Guarde LIVEKIT_API_KEY y LIVEKIT_API_SECRET — el Servidor 3 debe usar exactamente el mismo par.

3Servidor 3 — Aplicación

1 · Copiar los archivos e iniciar sesión

cd bot_factory                                 # del zip
docker login crvozimages-h3a3g5dzbkamfpd8.azurecr.io -u YOUR_USERNAME

2 · Completar el .env

Copie la plantilla y complete los valores que conectan los tres servidores:

cp .env.example .env
nano .env
APP_DOMAIN=app.sudominio.com                   # el dominio de este servidor
TLS_CERT=/etc/nginx/certs/fullchain.pem        # su certificado, copiado en ./certs
TLS_KEY=/etc/nginx/certs/privkey.pem
ALLOWED_ORIGINS=https://app.sudominio.com
PUBLIC_SPA_INDEX_URL=https://app.sudominio.com/index.html

SQL_HOST=192.168.1.10                          # Servidor 1
SQL_USER=botfactory
SQL_PASSWORD=YOUR_SQL_PASSWORD

LIVEKIT_HOST=192.168.1.20                       # Servidor 2 (interno, para :7880)
LIVEKIT_PUBLIC_HOST=wss://voice.sudominio.com
LIVEKIT_API_KEY=botfactory                      # igual que en el Servidor 2
LIVEKIT_API_SECRET=MISMO_SECRETO_DEL_SERVIDOR2
Dos reglas: la clave y el secreto LIVEKIT_* deben ser idénticos a los del Servidor 2, y ENCRYPTION_MASTER_KEY debe generarse con openssl rand -base64 32. Los demás secretos de la plantilla ya vienen generados.

3 · Levantar todo

docker compose -f docker-compose.stack.yml pull
docker compose -f docker-compose.stack.yml up -d

5 contenedores en Up; la API crea las tablas de la base de datos al arrancar por primera vez.

Si algo falla

SíntomaSolución
La API se reinicia / "cannot open database"Revise SQL_HOST/USER/PASSWORD, que el 1433 esté abierto desde el Servidor 3, y que el usuario pueda crear la base de datos.
"master key must be 32 bytes"Regenere ENCRYPTION_MASTER_KEY con openssl rand -base64 32 y ejecute up -d.
El agente nunca registra "registered worker"El Servidor 3 no alcanza el 7880 del Servidor 2, o las claves LIVEKIT_* no coinciden. Hágalas idénticas.
La llamada conecta pero no hay sonidoAbra UDP 50000-50100 y TCP 7881 hacia internet en el Servidor 2.
No hay certificado HTTPSVerifique que TLS_CERT y TLS_KEY apunten a archivos dentro de certs/, y que el certificado cubra el dominio e incluya la cadena completa. El contenedor registra en su log el modo que eligió al arrancar.

Actualizar desde la v1.0

Solo cambia el proxy web. Mismas imágenes, mismos puertos, misma base de datos, y los valores que ya tiene en el .env se mantienen — solo agrega dos líneas que apuntan a su certificado. Toma unos 15 minutos por servidor; el servicio se interrumpe únicamente los segundos que tarda cada contenedor en reiniciar.

Tenga a mano el certificado y la llave de cada dominio, en formato PEM. ¿Está haciendo una instalación nueva? Sáltese esta sección.

docker compose -f docker-compose.livekit.yml up -d
Dónde va su dominio y su certificado. En nginx/site.inc, que es nginx normal: 
server_name         voz.sudominio.com;
ssl_certificate     /etc/nginx/certs/fullchain.pem;
ssl_certificate_key /etc/nginx/certs/privkey.pem;
Las rutas son las que ve nginx dentro del contenedor: el compose monta ./certs en /etc/nginx/certs. Si sus archivos viven en otro lugar, cambien el montaje en el compose y esas rutas.

site.inc es suyo — al actualizar reemplazamos default.conf y nunca ese archivo. Tras editarlo: docker compose -f docker-compose.livekit.yml exec nginx nginx -s reload.

Verifique: curl -s https://<su dominio>/ responde OK. Si nginx no arranca, docker logs bf-livekit-tls dice por qué — casi siempre cannot load certificate, que significa que la ruta de site.inc no coincide con dónde están sus archivos.

Diagnóstico

diagnose.sh, incluido en los archivos de despliegue que descargó, revisa un servidor — contenedores, puertos, certificados, la conexión a la base de datos, la conexión con LiveKit y los errores recientes de los logs — e imprime un resumen de qué funciona y qué no.

Ejecútelo desde la carpeta donde está el archivo compose. La forma más rápida, sin descargar nada, es pedirlo al propio servidor de la aplicación:

cd ~/botfactory        # o ~/livekit en el servidor de voz
curl -fsSL https://app.sudominio.com/deploy/diagnose.sh | bash

Si prefiere revisarlo antes, o si el servidor no tiene salida a internet, use la copia incluida en los archivos de despliegue que descargó:

bash diagnose.sh

Desde el mismo lugar puede descargar siempre la última versión de los archivos de despliegue:

curl -fsSLO https://app.sudominio.com/deploy/docker-compose.stack.yml
curl -fsSLO https://app.sudominio.com/deploy/docker-compose.sql.yml    # solo si usa SQL en contenedor
curl -fsSL  https://app.sudominio.com/deploy/bot-factory-deploy.zip -o bot-factory-deploy.zip

Requiere bash: si lo canaliza a sh el script se detiene y se lo indica.

Ejecútelo en ambos servidores — cada uno solo ve su lado de la conexión. Si algo falla, guarde la salida y envíenos los dos archivos:

bash diagnose.sh > diagnostics-$(hostname).txt 2>&1

Es un archivo de texto plano que puede revisar antes de ejecutarlo. No se conecta a internet, no modifica nada en el servidor y no imprime contraseñas, llaves ni certificados — los secretos aparecen únicamente como "set (44 characters)".

Revisar desde afuera

Ejecutado en un servidor, el script solo puede comprobar que un puerto está abierto en esa máquina: si un firewall perimetral bloquea el 7881, la revisión igual pasa y ningún navegador puede conectarse. Pásele los dominios públicos y hace las mismas preguntas desde donde está el usuario. Ejecútelo desde su computadora, no desde los servidores:

bash diagnose.sh --app app.sudominio.com --livekit voz.sudominio.com

Resuelve el DNS, negocia el certificado en vivo, confirma que el 7881 se alcanza y que el 7880 no, verifica que los puertos internos (30000/30001/30003/31433) estén cerrados desde afuera, mide el desfase de reloj y comprueba que el servidor de voz que anuncia la aplicación sea el que realmente responde.

Si el dominio resuelve a una dirección de la propia máquina o a una dirección privada, el reporte lo advierte: esa ejecución no viene realmente de afuera y no prueba lo que un navegador en internet ve.

Historial de versiones

Esta página siempre describe la versión actual. Si tiene una versión anterior instalada, siga primero Actualizar desde la v1.0.

v1.1 — actual

  • El proxy web de ambos servidores Docker ahora es nginx.
  • Usted instala su propio certificado SSL. Coloque el certificado y la llave en una carpeta certs/ junto al archivo compose y apunte TLS_CERT y TLS_KEY a ellos en el .env.
  • Si deja TLS_CERT y TLS_KEY vacíos, se sirve HTTP simple en el puerto 80, para despliegues donde su propio proxy al frente maneja el HTTPS.
  • Nuevo script diagnose.sh en los archivos de despliegue: revisa un servidor e informa qué funciona y qué no.
  • IMAGE_TAG en el .env fija el despliegue a una versión específica (por defecto, la última).

v1.0

  • Primera versión del despliegue en tres servidores: SQL Server externo, un servidor de voz dedicado y un servidor de aplicación.

Inicio de sesión en producción (GOB-ID)

La plantilla viene con el inicio de sesión de prueba Fake-ID (AUTH_USE_FAKE=true). Para usar el inicio de sesión real de GOB-ID, cambie AUTH_USE_FAKE=false y complete los valores GOBID_* (comentados en .env.example) con los parámetros de su integración con GOB-ID. Es un cambio solo de configuración — las mismas imágenes.

La URL de retorno está fijada en el registro de la aplicación en GOB-ID. Si publica el sistema en un dominio distinto al registrado, el inicio de sesión redirige al dominio anterior y no completa. En ese caso hay que agregar https://<su-dominio>/auth/callback al registro de la aplicación en GOB-ID.
