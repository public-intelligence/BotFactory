# Changelog

All notable changes to Bot Factory will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Security
- **`diagnose.sh` no longer carries the support drop-box key.** The write-only upload key was hardcoded in the script; it now comes from the `SUPPORT_KEY` environment variable, and `--external` stops with a clear message when it is not set.
- **The ElevenLabs API key no longer reaches call participants.** Voice rooms carried the organization's key in `room.metadata`, which LiveKit delivers to everyone in the room, so any visitor of a public voice bot could read it. The key now travels in the agent dispatch metadata (`ctx.job.metadata`), which only the dispatched worker receives. This adds no latency and no new endpoint. The agent still accepts the key from `room.metadata`, so the API and the agent can be updated in either order; that fallback can go once every deployment runs this version. Deployments that served public voice bots should rotate their ElevenLabs key.

### Fixed
- **Embed iframe 503 on Docker installs behind a reverse proxy / without hairpin.** `/api/embed/{publicId}` fetched the SPA shell only from `PUBLIC_SPA_INDEX_URL` (the public hostname). On hosts where that name does not route back to the app container (common with an edge proxy), the API timed out and returned `Embed shell unavailable` even though `bf-frontend` was healthy on the compose network. The API now loads the shell via `bf-frontend:443` first (TLS Host/SNI = the configured https SpaIndexUrl, or the embed request host when SpaIndexUrl is empty/http/`bf-frontend`), then falls back to the public URL and `wwwroot`. Azure/SWA deployments without that container name keep the previous public-URL path after a short DNS miss.
- **The Registros page was showing DEBUG and TRACE noise no matter what `Logging:LogLevel` said.** `builder.Logging.AddSerilog(logger)` does not only register the provider — it also installs an `AddFilter<SerilogLoggerProvider>(LogLevel.Trace)` rule, on the assumption that Serilog does its own filtering. The file sink was configured `MinimumLevel.Verbose()`, so the two together pinned the log file at Verbose for every category and made it ignore the configuration entirely, while the console (default providers) correctly honoured `Information` / `Microsoft.AspNetCore: Warning`. The result: a log window where a single `GET /api/logs` produced roughly thirty lines — Kestrel connection accepted/started/stopped/FIN, four routing DEBUG lines, the EF connection open/close pair, the session-lookup SQL — and the page, which polls every 5 seconds, was mostly watching itself. Registering the provider directly puts the file sink under the same rules as everything else, so one knob (`Logging__LogLevel__Default`, or any per-category variant, set as an environment variable in compose) now governs both console and file. `Microsoft.EntityFrameworkCore.Database.Command` is additionally pinned to `Warning` in `appsettings.json`, since at the default `Information` it logs the full SQL of every query and the viewer's own session lookup alone would dominate the window.
- **Every line in the Registros viewer re-rendered on each refresh.** The list is a sliding tail but was tracked by `$index`, so after each poll index 0 pointed at a different entry and Angular rewrote all 500 rows in place — the whole log repainted every 5 seconds. Rows are now keyed by their content, with an ordinal suffix for identical repeated lines so the keys stay unique.
- **Log timestamps read as relative times.** They were rendered with `toLocaleString('es', { month: 'short' })`, which prints August as `ago` — so `7 ago, 11:51:15` looked like "7 minutes ago" rather than "7 August". Timestamps are now all-numeric and big-endian — `2026-08-07, 11:51:15` — and levels use Serilog's own `VRB`/`DBG`/`INF`/`WRN`/`ERR`/`FTL` instead of translated labels: the log lines are the server's output and are shown verbatim, in English, with only the surrounding page chrome translated.

### Changed
- **UI-Core is now `@public-intelligence/ui-core` `^0.0.16`**, the version the frontend is built and tested with. It installs from the organization's GitHub Packages registry; the Azure DevOps feed is no longer used.
- The development sign-in users (`AUTH_USE_FAKE`) use `@example.com` addresses and the organization «Demo». Defaults that pointed to the previous deployment's hostnames (`diagnose.sh --external`, the embed test harness) now use `example.com` placeholders.
- The default logo is now `cupula-gob-azul.webp`.
- **`diagnose.sh` stops instead of producing a report it cannot stand behind.** When the deployment directory cannot be found, carrying on does not yield a shorter report — it yields a wrong one: every value that lives in `.env` reads as unset, and unset is indistinguishable from broken. A run in exactly that state announced *"LiveKit is NOT reachable — no call can be answered"* while LiveKit was answering normally, purely because `LIVEKIT_HOST` had nowhere to come from. It now fails fast with the reason, the `docker inspect` command that locates the directory, and a note that the command itself is unchanged once you are standing in it. Two deliberate exceptions: `--app`/`--livekit` runs continue, since those probe a hostname from outside and never touch `.env`, and `--external` still ships the bundle, because the upload runs from an `EXIT` trap — so support sees the stop rather than silence.
- **`diagnose.sh` asks Docker where the deployment lives instead of guessing.** It looked for the compose file in `$PWD` and three hardcoded home directories, which cannot survive `curl … | sudo bash` (where `$HOME` becomes `/root`) or a directory nobody thought to list. Three consecutive runs on a live deployment were lost to it, and the damage went well past `--update` doing nothing: no compose file means no `.env`, which silently empties the whole Configuration section and turns every check that reads it into a phantom — one run reported LiveKit unreachable and "no call can be answered" while LiveKit was answering normally, purely because `LIVEKIT_HOST` had nowhere to come from. Compose stamps the launch directory onto every container it creates, so the directory is now read from `bf-api`/`bf-frontend`/`bf-livekit` first and the old guesses remain as a fallback. When both fail, the two messages now name the file, say what was not checked and why, and print the `docker inspect` command that answers the question — rather than "run it from the deployment directory", which is the instruction that kept not landing. Verified against a container carrying the real label from an unrelated directory (found), a label pointing at a directory with no compose file (falls through), and a container with no label at all (falls through).
- **`--update` drops a stale registry login instead of failing on it.** The registry serves anonymous pulls and every image in the stack comes from it, so a stored `docker login` buys nothing — and costs something: Docker sends a stored credential in preference to pulling anonymously, so the day it expires the pull fails with `unauthorized` on a deployment that needed no credentials at all, and the error sends the operator hunting for a password that is no longer required. That is how a customer sat on a week-old frontend image while every other check passed. `--update` now removes the login before pulling, and only then — the removal is gated on the registry actually answering an anonymous token request, which costs one HTTP call, because if the registry is ever closed again that login becomes the only way in and dropping it would take the deployment offline. Nothing happens outside `--update`: a plain run still changes nothing. The failure message for a genuinely private registry now says so rather than blaming an expired login. Both helpers verified against the live registry (open registry, unknown repository, unresolvable host) and against real Docker config files, including the `sudo docker` case where the credential that matters is root's, not the invoking user's.
- **`diagnose.sh`'s summary now lists what works as well as what does not.** It ended with failures and warnings only, so a passing run finished with a bare count and the reader had to scroll the whole report to see what had actually been verified — and on a failing run, the working half was equally invisible. The summary is now three lists: **NOT working** (`✗`, full text, since there the explanation is the fix), **Warnings** (`!`), and **Working** (`✓`, claim only — the trailing "— why it matters" clause is noise once a check has passed). Someone can now paste just the summary and it carries the state of the deployment.
- **`update.sh` has been absorbed into `diagnose.sh` as `--update`.** One command — `bash diagnose.sh --update` — now pulls the latest images, recreates what changed (`--remove-orphans`, SQL overlay included), waits for containers to settle (running, healthy where a healthcheck exists, not restart-looping — a crashed container is reported with its last 40 log lines inline), and then runs the **entire diagnosis against the post-update state**: strictly more verification than the standalone script did, with one script to distribute instead of two. `--dry-run` reports what would change without restarting; `--external` ships the whole run to support. `update.sh` remains as a shim forwarding to `diagnose.sh --update`, so old runbooks and bookmarked URLs keep working. Verified live: the settle check catches a crash-looping container (`state=restarting exit=1`) with its logs inline, and a pull failure downgrades the run gracefully — the checks then describe the unchanged deployment and say so.
- A host serving both the web app and LiveKit signalling on one domain no longer fails the outside-in health check. The check demanded LiveKit's plain-text `OK` at `/`, but that layout serves the SPA there and routes only `/rtc` and `/twirp` to LiveKit — a supported arrangement the check called broken. It now recognises an HTML response at `/` as the combined layout and relies on the signalling check, which is the real health signal. A genuinely wrong body is still a failure, now truncated to 80 characters: the raw echo printed an entire HTML document into the summary.
- **`diagnose.sh` tests outbound internet by default, and actually connects.** The old check was opt-in (`--egress`) and only resolved DNS — on a network that blocks or intercepts outbound 443, the name resolves fine and the TLS handshake is then reset, so the check would have passed while KB indexing jobs died on `SSL connection could not be established ... Connection reset by peer`. It went unnoticed for days precisely because nobody opted in: four consecutive support reports carried the `[SKIP]`. Now every server-mode run performs a bare TLS connect to each provider — Gemini (chat + KB indexing), ElevenLabs (voice synthesis) and the image registry (updates) — from inside a container where one carries curl, so the test exercises the same DNS and network path as the services. Failures name the provider and the failure mode outright: does-not-resolve, refused, silently dropped (firewall — open outbound 443), or handshake reset (interception — ask whether egress requires a proxy, then `HTTPS_PROXY` must be configured). `--no-egress` opts out; `--egress` remains accepted for old runbooks.

### Added
- **«Respaldo obligatorio»: a bot can be held to answer only from its sources.** A new per-bot switch (`RequireGrounding`, off by default; migration `AddBotRequireGrounding` adds the column) for bots that must never state a datum they were not given. With it on:
  - the first Gemini call of every turn must consult a source (`functionCallingConfig.mode = ANY`), and the following ones are free; the bot answers at a lower temperature (`Gemini:GroundedTemperature`, 0.1);
  - the tool lookups behind the last three answers ride in the history (results trimmed to 2 000 characters), so the model sees question → lookup → answer instead of answers that seem to come from memory, which it used to imitate in long conversations;
  - a **grounding gate** holds the answer sentence by sentence and delivers a sentence only if every concrete datum in it — phone, service code (`*462`), link, e-mail, amount (in digits or in Spanish words: «seis mil setecientos pesos»), any other number of three or more digits — appears in the evidence: the bot's prompt, what the user said, the results of its tools in this turn and in the re-sent history. In a contact line only the unsupported items are dropped. When something is dropped, the bot's grounded-only message closes the answer (`grounding_blocked` event per datum; `turn_without_tool` if a turn consulted nothing);
  - a forced lookup that finds nothing no longer short-circuits to the grounded-only message, so "gracias" is not answered with "no tengo esa información"; the gate still keeps any invented datum out.

  The check is deterministic: it verifies data, not meaning — a wrong claim made only in words is outside its reach. The switch is in the bot's General tab, next to the grounded-only message.

### Changed
- **Chat answers are laid out for reading.** The backend turned every line break of the model's answer into a space, for every channel, so a list of requirements reached the chat as one long paragraph. Line breaks are now kept for the chat (the stored message and the hub deltas) and flattened only on the voice SSE, so speech is unchanged and no SSE frame breaks. The chat renders assistant answers as paragraphs, bullet and numbered lists (marker in its own column, hanging indent), headings, bold (`**…**`) and links, markdown links included; a sentence that introduces a list ("Los requisitos son:") shows in bold. Answers stored flattened before this change are rebuilt from what survived: double spaces, "•" bullets, and "- " or "1. " items right after a sentence ends (only when there are at least two, so "8:00 a. m. - 5:00" stays as written). Rendering goes through Angular's escaping; there is no `innerHTML`.

### Fixed
- **Street numbers and postal codes are no longer phone links.** Any 3–6 digit number became a tappable phone ("1038 Brickell Avenue", "Suite 410", "Florida 33131"). A bare short number is now a phone only after words that say so ("llame al 911", "línea 1311"), and star service codes such as `*462` are recognized and dial with their star.
- **A message with several questions no longer ends in "Lo siento, no pude procesar eso."** A turn allowed two tool calls and acted only on the first function call of each Gemini answer, so a message asking three things or more spent one Gemini pass per lookup, hit the cap and threw the whole answer away. Every function call of an answer now runs before the next Gemini call, the budget is six tool executions per turn (`Gemini:MaxToolIterations`, was 2), and running out of it no longer fails the turn: one last pass with tools forbidden (`functionCallingConfig.mode = NONE`) answers with what was gathered and says what could not be consulted.
- **A tool the bot does not have, or one that throws, no longer fails the turn.** The model once asked for a tool that does not exist and the exception ended the turn in the fallback message. Both cases now come back to the model as an error result it reads, and the bot says it could not consult that instead of inventing the answer (`tool_call_unknown` / `tool_call_failed` events).
- **Transient Gemini failures are retried once.** A 429, a 5xx, a timeout or a dropped connection gets one more try (after `Gemini:RetryDelayMilliseconds`, 1.5 s; a 429 waits twice that), but only while that call has streamed no text, so the user never hears words repeated. A 400/401/403 is not retried. Each retry is an `llm_retry` event.
- **A Gemini call can no longer hang the turn.** `HttpClient.Timeout` stops guarding once the response headers arrive, and the answer is read as a stream, so a stream that stalled halfway had no limit at all. One limit now covers the whole call (`Gemini:HttpTimeoutSeconds`, raised from 30 to 60) and surfaces as a retryable timeout, distinct from a cancellation by the caller. The voice agent needs no change: the API already sends SSE keepalives every 5 s while it works.
- **An answer cut at the output limit is finished instead of left half-written.** A long answer could stop in the middle of an e-mail address or a link (observed: `info@pgr.gob`). When Gemini reports `finishReason: MAX_TOKENS`, what was streamed stays and one more pass, tools forbidden, continues exactly where it stopped (`llm_truncated` event; at most once per turn).

### Added
- **Gemini token usage is recorded on every call.** Bot Factory ignored the `usageMetadata` that Gemini returns, so the logs showed no tokens and nobody could confirm that Gemini's implicit prompt caching was working. Each Gemini call now emits an `llm_usage` telemetry event with the prompt, cached, output and thinking tokens plus the share of the prompt served from cache, and writes one `Gemini usage …` line to the log (visible in Registros). The per-turn `backend_completed` event carries the turn totals and the tokens of each Gemini span, and the conversation feed shows them in the turn summary. Two edge cases are handled on purpose: a call for which Gemini sends no `usageMetadata` is recorded as not reported (and warned about) instead of as zero tokens, and a call cut short by barge-in or an error still records the tokens Gemini had already counted. Recording never affects the answer: if it fails, the turn carries on. Gemini repeats `usageMetadata` on every streamed chunk with running counts, so the last one wins; the usage is parsed before the parts of each chunk so that stopping the read at a function call cannot lose it. No migration: the numbers live in the event's existing JSON `Data` column.
- **P2 test coverage** for tool execution internals (policy, credentials, gateway, kb_search handler), audit/telemetry/system-log HTTP APIs, kb-scraper mocked render tests, frontend bot-admin Vitest helpers (conversation-item, chat-history, tools mapping, store, filter-ui), and optional Playwright smoke harness (`npm run test:e2e`, skips without `E2E_BASE_URL`). `make test` includes mocked kb-scraper tests; e2e is not in CI gates.
- **P1 test coverage** for tools admin CRUD, tenant/public-token/permission middleware, bot publish and media HTTP, frontend auth stack (guard/service/interceptor Vitest), and CI wiring (`make test`, Azure FE/agent pipelines, GHA FE+agent jobs). No live ElevenLabs or tool probe networks in CI.
- **P0 test coverage** for public/embed HTTP, auth/session, ConversationHub (SignalR + fake Gemini), frontend chat helpers/services (Vitest), and agent LLM/relays/helpers (pytest) — deterministic, no real GOB-ID / LiveKit cloud / Gemini / ElevenLabs. CI wiring deferred to P1.
- **The frontend container image is now built and pushed by CI, in parallel with the Static Web App deploy.** `.azure/frontend.yml` only ever deployed to the SWA — it has never contained an image build in its history — so `bot-factory-frontend` was published by hand, and every Docker deployment ran whatever was last pushed manually. On 2026-08-06 that meant a customer's `diagnose.sh --update` correctly reported *"already current"* against an image from 2026-07-30, a week behind `main`: branding, the Registros page and the `product-url` fix had all shipped to the SWA and reached no Docker install at all. The pipeline is now two independent jobs rather than a chain — both need the same commit, neither needs the other's output, and gating the SWA behind an image build would only delay what most users see. The image job writes `.npmrc` from the pipeline secret rather than relying on the copy committed to the repo, so it keeps working once that file is removed. Adds `apps/frontend/.dockerignore`, since `az acr build` uploads the context and `node_modules` has no business in it.
- Organization logo and favicon can be uploaded from Settings (Marca). The logo appears in the admin sidebar; the favicon is used in the admin app and on public chat/embed tabs. Defaults remain the government cupola assets when nothing is uploaded.
- Per-bot **Apariencia** tab: upload a logo and set background, primary, and accent colors. Public and embed chat apply the theme via CSS variables, show the logo in the header (not the landing hero circle), and keep the previous dark defaults when branding is unset.
- **Support-bundle relay at `POST /v0/api/logs` — customer networks now need egress to one host only.** `diagnose.sh --external` used to ship bundles straight to the support drop box, which meant asking a customer's network team to allowlist an unfamiliar domain. The bundles now go to the platform's own deployment (`https://bf.example.com/v0/api/logs`), where a new anonymous API endpoint forwards them — body, query and bearer key untouched — to the drop box and returns its response, so the reference-id flow is identical. The public path lives outside `/api` on purpose (a Static Web App rewrite and an nginx `location` map it to the endpoint) so nothing about existing API routing changes. The relay holds no secrets: the caller's key passes through and the drop box validates it; a missing key is rejected at the relay (401), a wrong one by the drop box (403). Verified end to end: upload through the relay returns the drop box's 201 and id.
- **"Registros" admin page — the API's logs, readable from the browser.** The API now writes every log event to a single ~25 MB rolling file (CLEF JSON, newest wins, no cleanup job needed) alongside the unchanged console output, and two new admin-only endpoints read it back: `GET /api/logs` returns the parsed tail with level/text filters, `GET /api/logs/raw` streams the file for download. The new **Registros** page (at `/logs`, deliberately not in the sidebar; superadmin/bot:admin only, same gate as the Hangfire dashboard) shows a live console-style view — auto-refreshes every 5 seconds, filter by minimum level, search, one-click download — so an operator can see why something failed (KB indexing, startup, DB errors) without SSH or `docker logs`. The compose files mount a named volume at `/app/logs` so the log survives container recreation. Console output is byte-identical to before: `diagnose.sh`'s `docker logs` greps keep working.
- **`--external` on `diagnose.sh` and `update.sh` ships the run's logs to support.** When passed, the script sends its own report plus the last 1500 log lines of every `bf-*` container to the support drop box and prints a reference id to quote — replacing the copy-paste round trip where an operator screenshots a terminal and support asks for the part that scrolled off. Off by default and deliberately so: container logs can contain user conversations, so shipping them is an explicit per-run decision, announced up front in the script's own output. The upload key is write-only — it can add a file to the drop box and nothing else, not list or read back. Bundles are capped (1500 lines per container, 2000 chars per line, 8 MB total); without outbound internet the run still completes and only the shipping step reports failure. Verified end to end: uploaded, fetched back byte-for-byte, and the failure path (unreachable endpoint) leaves the run's exit code untouched. The drop box URL appears nowhere in the printed output or the shipped bundle — the operator-facing text says only "Bot Factory support"; the endpoint lives in the script source alone.
- **`update.sh` — one-command update for the Docker servers** (`deploy/update.sh`, also served at `/deploy/update.sh`). Releases are distributed by publishing images to the registry and having operators pull; this script makes that safe: it detects which server it is on (SQL overlay included), runs `compose pull`, recreates only the changed containers with `--remove-orphans`, then **verifies the result** — every container running, healthy where a healthcheck exists, and restart counts watched long enough to catch a crash loop. `docker compose up -d` alone exits 0 even when a container starts and immediately dies, which turns a broken update into "update done" followed by a user complaint hours later. On any failure it prints that container's last 40 log lines so the report reaching support names the problem; a pull rejected with `unauthorized` points at the expired registry login. `--dry-run` reports what would change without touching anything. Verified against a live stack: healthy path, crash-loop path (caught, logs printed, exit 1), and dry run.
- **`diagnose.sh` now checks that the deployment's addresses line up**, in a new *Addressing* section (this host's IPv4 addresses, each marked public or private) and a *Reachability from browsers* section on the application server. A split deployment fails in a way no existing check caught: both halves report healthy and the addresses simply do not match. It now resolves the host in `ALLOWED_ORIGINS` and fails when it points somewhere other than this machine — a real deployment had it naming the LiveKit server, so browsers would have been told an origin the app server never sees. It fails when the host holds only private addresses while `ALLOWED_ORIGINS` promises a public one, because internet users then cannot reach the app at all, and it names the two ways out (publish the host, or reverse-proxy it from the LiveKit server, which already has a public address and an nginx). It warns when `LIVEKIT_HOST` resolves to a public address, since that server-to-server hop should take the private path rather than depend on the perimeter hairpinning. An intranet-only deployment stays quiet: private addresses are only reported as a problem when the configuration claims otherwise.

### Changed
- **Voice contact card can be dismissed with a close button.** The card still clears on the next interaction; the new control lets users hide it without pausing or ending the session.
- **`check-public.sh` is gone; it is now a mode of `diagnose.sh` (v2.0).** Two scripts meant operators had to know both existed, fetch both, and remember which answered which question — and the halves had already drifted into two copies of the same certificate, DNS and HTTP helpers. `bash diagnose.sh` still checks the server it is run on; `bash diagnose.sh --app <host> --livekit <host>` runs the outside-in checks; on a server, passing the hostnames runs both and prints one summary. The header, `--help` and the closing advice now point at the other direction rather than at another file.

### Added
- **Blob assets are addressed by version, so browsers fetch each one exactly once.** Every upload already minted a fresh GUID into the storage key, which makes it a token that provably changes whenever the bytes do — it was simply never sent to the client, so the frontend cache-buster fell back to the filename and re-uploading `logo.png` produced a URL identical to the old one. `BotResponse` and `OrgBrandingResponse` now carry `logoVersion` / `faviconVersion` / `thinkingSoundVersion`, read straight out of the existing key: no new column, no migration, and every asset already in production has one from the moment this deploys. A request whose `?v=` matches the current version is answered `max-age=31536000, immutable` (`public` for the by-slug routes, `private` for admin — scope is preserved), so a repeat visitor issues no request at all rather than a 304. `immutable` is unrevocable, so it is gated on that match: a request with no `?v=`, a stale one, or a URL from a bookmark or a still-loaded older SPA build gets the revalidating tier and still sees the current asset. The public favicon-by-slug route has no version available to the client and stays on the five-minute tier.

### Fixed
- Text chat no longer draws the first message under the logo/name header on mobile. The session view reserves space for the absolute header so bubbles start below it.
- **The thinking sound answers byte-range requests, so Safari will play it.** Safari treats range support as a precondition for playing media rather than an optimisation: it probes with a `Range` request and can decline to play at all when the server replies `200` with the whole body. The SAS URLs these endpoints replaced pointed straight at storage, which honours `Range` natively, so proxying the bytes through the API is what put custom thinking sounds at risk of silently not playing on Safari and iOS. The two thinking-sound routes now buffer the blob — a `MemoryStream` can seek, which is the only thing ASP.NET needs before it takes over the whole protocol (`Range` parsing, `If-Range`, `206` with `Content-Range`, `Accept-Ranges`, `416` on unsatisfiable), so no range handling is ours to write. Buffering rather than asking storage for a seekable stream keeps this to the single round-trip already being made; the alternative costs a second call for the metadata and reintroduces the delete-mid-request race that call was collapsed to avoid. Deliberately opt-in and limited to audio: nothing ever sends a `Range` for an `<img>`, so logos and favicons keep streaming. Upload caps bound the buffer at 5MB and versioned URLs cache immutably, so a client buffers a given sound at most once.
- **The OpenAPI document's binary responses now come from code instead of a hand-patch.** The `application/octet-stream` response bodies had been written into `BotFactory.Api.json` by hand; regenerating the document erased them, and the frontend client then typed the eight download endpoints as `string` instead of `Blob`, corrupting every download. The endpoints declare `.Produces<byte[]>(200, "application/octet-stream")` and a document transformer marks those bodies `format: binary` (the generator's own `format: byte` means base64, which ng-openapi-gen reads as a string). Regenerating now reproduces the previously hand-written bytes exactly. Worth noting the CI guard could not have caught this: "Check OpenAPI spec is up to date" runs `git diff` after a build with `OpenApiGenerateDocumentsOnBuild=false`, so it compares the file against itself.
- **Streamed blob downloads now cache properly and can no longer 500 on a mid-request delete.** The streaming endpoints sent no `ETag`/`Last-Modified`/`Cache-Control` at all, so every public chat load re-downloaded the full logo and thinking sound; they now emit both validators and honour `If-None-Match`/`If-Modified-Since` with a bodiless 304. The anonymous by-slug routes send `public, max-age=300` (shared caches may store; a re-uploaded asset propagates within five minutes since the URL is stable and serves whatever the current asset is); the authenticated admin routes send `private, no-cache` (an intermediary must never cache a tenant's asset, and an admin who just replaced a logo must see the new one immediately — every use revalidates, which is a cheap 304). Separately, the blob open collapsed from three storage round-trips (`Exists` → `GetProperties` → `Download`) to one: the pre-checks were stale by the time the download ran, so a blob deleted in that window surfaced as an unhandled 500 instead of the 404 it now is.
- Blob downloads (org logo/favicon, bot Apariencia logo, thinking sound, KB files) are streamed through the API instead of Azurite SAS URLs. Docker deploys expose Azurite only on the internal network (`bf-azurite`), so browsers could not load those assets even though uploads succeeded.
- Chat “Conectando…” screen stays readable on light Apariencia themes. The spinner and subtitle still used white / `text-neutral-300` from the dark default, so on cream backgrounds the label nearly vanished; they now follow `--bf-fg` / `--bf-accent` / `--bf-muted`.
- **Agent and frontend deploy pipelines after test gating.** Azure Agent CI called `uv` without installing it (`command not found`). Frontend Vitest expected contact extract without `emails` after emails landed on `main`, and `dismissContactCard` was `private` while the template binds `(closed)` — which also broke production `ng build`.
- **Voice replies that promised a link “en pantalla” but never included a URL.** The global speech prompt now requires canonical `https://…` URLs, digit phones (including short codes like `1311`), and `user@domain` emails in the same message; bare domains, emails, and short service numbers are detected for the contact card, chat linkify (`tel:` / `mailto:`), and TTS sanitization.
- **The new redirect-loop check called a working site down.** It reported a loop whenever nginx redirected on `X-Forwarded-Proto: https` *and* `ALLOWED_ORIGINS` pointed somewhere other than this host — but those two facts do not add up to a loop. A proxy pointed at this host's `:443` never sends a plaintext request, so the redirect never fires and the site serves perfectly; the check announced "the site is down from outside" while it was up, which is precisely the kind of false failure that trains operators to skim past the real ones. The verdict now belongs to the probe that actually followed the redirects: `[FAIL]` only when the loop was observed, `[INFO]` when the public name demonstrably reaches this host anyway (the proxy is on `:443` — worth fixing before someone repoints it at plain HTTP, but nothing is broken), and `[WARN]`, naming both possibilities, when the proxy could not be reached to tell which.
- **The application server's nginx put the whole site into a redirect loop behind a reverse proxy.** The `:80` block answered `return 301 https://$host$request_uri` unconditionally, which is right for a browser typing `http://` and catastrophic when another proxy terminates TLS in front: that proxy forwards over plain HTTP, this server replies "go to https://", the browser returns to the proxy, and round it goes until the browser gives up with `ERR_TOO_MANY_REDIRECTS`. The site is then down for everyone outside while every check on the app server still passes — and the layout that triggers it is the one this script recommends ("serve it through the LiveKit host's nginx, which already has one"). The two server blocks are now one listening on both ports, and the redirect is decided by `$fwd_proto` — the browser's real scheme, which already existed in the file for the API's benefit — instead of by the port the request arrived on. The proxy in front must send `X-Forwarded-Proto: https`; without that header no server can tell the two cases apart, and the file says so. Verified end to end against a two-container reproduction of the split layout: the old config loops (curl exits 47), the new one serves in a single request.
- **`diagnose.sh` called a working split deployment broken, twice per run.** It compared the address in `ALLOWED_ORIGINS` against the addresses this host holds and failed when they differed — but on a split deployment they *always* differ: the app server is private and a reverse proxy in front carries the public name. No address comparison can tell that apart from a real misconfiguration, so the check now asks instead of assuming: it fetches the SPA's runtime config through the public name and compares it byte-for-byte with the file this host serves. Same file means the proxy really does forward here (`[ OK ]`), a different application means browsers are reaching another machine (`[FAIL]`), and unreachable — normal when the network does not hairpin — is a `[WARN]` pointing at `--app` to settle it from outside. Two false failures became one accurate line.
- **New: `diagnose.sh` detects the redirect loop from both sides.** On the app server it asks the running nginx what it does with `X-Forwarded-Proto: https`; still redirecting means every page will loop the moment a proxy is put in front, reported as a failure when one already is and a warning when none is yet. From outside (`--app`), it follows the redirect chain and names the loop outright instead of reporting the bare `HTTP 301` the old check surfaced, which described the symptom without naming the cause.
- **An expired session whose refresh failed returned 500 instead of 401.** When the identity provider rejects a refresh, `SessionAuthHandler` deletes the session row and fails authentication — but the browser has several requests in flight at once, so they all arrive carrying the same dead session: the first delete wins and the rest raise `DbUpdateConcurrencyException` ("expected to affect 1 row(s), but actually affected 0"), which escaped into the exception handler as an unhandled 500. The deletion is the intended end state either way, so a lost race is now absorbed and every one of those requests answers 401 like the winner does. Seen live on the tica2 deployment, where a `gobid` refresh 404 produced one clean session removal and a stack trace beside it.
- **`diagnose.sh` hung for 20 seconds and then reported "could not read permissions" from the containerized database.** The `sa` password was read only from `.env`, which is readable only when the script runs from the deployment directory; run from anywhere else it came back empty, and an empty password does not fail — `sqlcmd` sits on an interactive `Password:` prompt until `timeout` kills it, which the report then quoted as *"the last operation was terminated because the user pressed CTRL+C"*. The password now comes from the `bf-sql` container's own environment (`MSSQL_SA_PASSWORD`), which is correct wherever the script is run from, and falls back to `.env`; with neither, the check skips with a clear reason instead of blocking on a prompt.
- The bundled `docker-compose.stack.yml` served at `/deploy/` was a version behind the one in `deploy/` — it was missing the `api_logs` volume, so a deployment set up from the download would have lost its Registros log on every container recreation.
- Chat branding polish: landing hero circle uses the accent color (like the listening bars) and no longer shows the logo in the center — logo stays top-left only. Status alerts (audio fallback / errors) use a fixed high-contrast danger style so they stay readable on light themes.
- **The outside-in port check called TLS-only ports blocked.** It probed with `curl http://host:port/`, which sends a plaintext request to a TLS listener, receives nothing, and times out — indistinguishable, in the old code, from a firewall dropping the SYN. Every run therefore reported `443/tcp is NOT reachable` for a host serving HTTPS perfectly well, i.e. a `[FAIL]` on the single most important port in the deployment. Reachability is now established with a `telnet://` connect probe, which asks only whether the TCP handshake completed (`%{time_connect}`) and layers no application protocol on top; where curl lacks telnet support it falls back to an HTTPS probe on 443 and retries any timeout over TLS before calling a port closed. The probe reads from `/dev/null`, because under the documented `curl … | bash` invocation stdin is the script itself and curl's telnet handler would have eaten it.
- **A missing `/api` proxy or `env.js` could pass.** The status code and the content type were fetched in two separate requests, and a server may answer a `HEAD` differently from a `GET` — an Azure Static Web App 404s the `HEAD` and 200s the `GET` of the same path — so the check compared the code from one response against the type from another and let an SPA fallback through as a working API. Both now come from a single `GET`, and HTML served where JSON or JavaScript belongs is reported as the fallback it is.
- `diagnose.sh` no longer aborts on a private-only host whose `ALLOWED_ORIGINS` is empty. `ORIGIN_IP` was only assigned inside the branch that parses the origin but read again outside it, so under `set -u` the run died mid-report — on exactly the misconfiguration the section exists to diagnose.
- Admin share/embed URLs no longer hardcode `https://bf.example.com`. Slug previews, copyable chat links, and iframe snippets now use the current deployment origin (or optional `PRODUCT_URL` / `window.__env.productUrl`), so installs like `bot.example.go.cr` and `bot.example.org` show their own host.
- Text chat no longer plays the typing/thinking sound while the bot is responding. That sound stays voice-only; text sessions show a typing-dots indicator instead until the reply starts streaming.
- **`agent registered with LiveKit` no longer passes when LiveKit is unreachable.** The check greps the agent's whole log for `registered worker`, which is a historical fact: an agent that registered at boot and lost LiveKit hours later still matched, so the report showed a green agent beside a red LiveKit and the green one looked like the more trustworthy of the two. It now qualifies that line with live reachability and, when the port is shut, says outright that the worker has dropped and no call can be answered.
- **`diagnose.sh` reported four healthy things as broken.** All four came from reading `.env` differently than Docker Compose does: `envval()` took the whole rest of the line, so a value with a trailing `# comment` carried the comment into every check. A reachable host was dialled as `10.60.17.150   # LiveKit host…:7880` and failed; a valid 32-byte key "decoded to 0 bytes" because the comment went to `base64 -d`; and a secret's reported length was the value plus the comment, making two servers that agreed look like they disagreed. It now strips an inline comment when the `#` follows whitespace and removes one layer of quotes, matching Compose — a `#` inside quotes, or with no space before it, stays part of the value.
- **`diagnose.sh` reported every wildcard certificate as not covering its own domain.** The SAN check compared literally (`grep -qx`), so `*.example.go.cr` never matched `bot.example.go.cr` and the script emitted a `[FAIL]` saying browsers would reject a certificate they accept. Matching now understands wildcards, which cover exactly one label — `*.example.com` matches `app.example.com` but not `a.b.example.com` — and is case-insensitive.
- **`diagnose.sh` could never read SQL permissions from the containerized database.** The call was `timeout 20 d exec …`, but `d()` is a shell function and `timeout` execs a binary, so it only ever produced `timeout: failed to run command 'd': No such file or directory` — surfacing as "could not read permissions" on every run. It calls `$DOCKER` directly now.
- **`diagnose.sh` demanded `SQL_HOST`/`SQL_USER`/`SQL_PASSWORD` even when SQL runs as a container.** The overlay ignores all three (`docker-compose.sql.yml` says so outright), so a correct deployment collected one `[FAIL]` and two `[WARN]`s for variables nothing reads. It now detects `bf-sql` and checks `SQL_SA_PASSWORD` instead.
- Missing TLS on the application server is now a `[FAIL]`, not a `[WARN]`. Browsers only grant microphone access in a secure context, so over plain HTTP `getUserMedia()` is refused and no call can start — while every other check still passes. Buried among other warnings it read as cosmetic; it is the one thing that stops a voice deployment working.
- `diagnose.sh`'s port checks no longer imply they tested reachability. They inspect local sockets, so `[ OK ] ICE/TCP fallback (from browsers)` was printed for a port a perimeter firewall was dropping. The wording now says the socket is bound on this host and that outside reachability is untested; the `--app`/`--livekit` mode answers the other half.
- `diagnose.sh`'s "recent errors" section no longer reports internet background radiation as a deployment problem. Vulnerability scanners probing `/manager/html` and malformed TLS handshakes from scanning hosts were surfacing as errors, as were EF Core migration DDL lines whose column names contain "Error" and the routine `Shutdown timeout:` message.
- `diagnose.sh` no longer dies with `Syntax error: "(" unexpected` when started as `sh diagnose.sh`. Debian/Ubuntu's `sh` is dash, which has no arrays, so it choked on the first `FAILURES=()`. The script now re-execs itself under bash — and when it was piped in (`curl ... | sh`) there is no file to re-exec, so it says so instead of running `exec bash sh`. Verified end to end on stock Ubuntu 20.04, 22.04, 24.04 and 25.04.
- The API now honours `X-Forwarded-Proto` (`UseForwardedHeaders`), so `Request.Scheme` reflects the browser's real scheme instead of the plain-HTTP hop from the TLS-terminating proxy in front of it (Azure App Service's front end; Caddy in the Docker deployment). Previously URLs the API handed back to the client — notably the Fake-ID login URL — came out `http://` on an otherwise HTTPS site, causing an extra redirect and a momentary "Not secure" flash. Only `X-Forwarded-Proto` is honoured; `X-Forwarded-For` is deliberately left off because it would rewrite `Connection.RemoteIpAddress`, which the rate limiter partitions on.
- Voice bots no longer keep answering the **previous** topic after a tool/function call. The turn orchestrator was dropping the user's current question from the second (answer-generation) Gemini pass whenever a tool ran, so the model latched onto the prior turn's topic until the user pushed back ("no es de eso"). The current question now stays in the request on every tool iteration — a regression of the earlier `firstUserText` turn-order fix, reintroduced when orchestration moved into `ChatTurnService`. Added unit and end-to-end regression tests. (planning/topic-switching-diagnosis.md)
- A voice turn cancelled mid-flight (barge-in or a superseded turn) persists the user message but no assistant reply, so conversation history could end on a dangling, unanswered user turn. The next turn then sent the model two consecutive user turns and it tended to answer the abandoned question. Such trailing unanswered user turns are now dropped from history before the next turn is built.

### Added
- **An outside-in mode for `diagnose.sh`.** Run from a laptop or any host that is not the servers: `bash diagnose.sh --livekit voz.example.com --app app.example.com`. It exists because a script running *on* a server cannot see what a browser sees — its port checks inspect local sockets, so a perimeter firewall dropping 7881 still passes them, and it reads the certificate off disk, which cannot detect a proxy in front, a wrong default server, or a chain served differently than stored. This one resolves DNS, negotiates TLS live against the machine's trust store, confirms 7881 is reachable and 7880 is not, and checks that the ports published for the compose network (30000/30001/30003/31433) are closed from outside — worth its own check because Docker's iptables rules are evaluated before ufw, so `ufw deny` does not close them. It also measures clock skew from the server's own `Date` header, which `timedatectl` cannot do (that reports whether NTP is *enabled*, not whether the clock is *right*, and LiveKit token expiry fails on the latter), and cross-checks that the LiveKit host named in the SPA's `env.js` is the one that actually answers — something neither server can verify alone. Uses only bash, curl and openssl; TCP reachability goes through curl rather than `nc`, whose connect-timeout flag is spelled differently on macOS and Linux, where guessing wrong leaves a filtered port hanging for the kernel's full SYN timeout. It states plainly what it cannot prove: media actually flowing, since LiveKit allocates UDP 50000-50100 per call and an idle server has nothing bound there. It also refuses to pretend: when the hostname resolves to an address the running machine holds, or to a private address, it warns that the run is not really coming from outside — a perimeter that does not hairpin lets a server check its own public name successfully while the internet cannot reach it at all.
- **SQL Server in a container as an alternative to the external database** (`deploy/bot_factory/docker-compose.sql.yml`), for pilots, demos and test installs where provisioning a Windows database server first is the thing blocking a deployment. It is an overlay rather than a second full stack — `docker compose -f docker-compose.stack.yml -f docker-compose.sql.yml up -d` — so the API, agent and frontend keep exactly one definition and cannot drift apart; the overlay holds only what actually differs (the SQL service, the connection string, one extra `depends_on`). Runs **SQL Server 2025** (`mcr.microsoft.com/mssql/server:2025-latest`); the full migration set was verified to apply against it. SQL's port is published on loopback only, since the `sa` account is behind it. Defaults to the Developer edition, which is free but **not licensed for production** — `SQL_EDITION=Express` or the external server are the production options; that is left as an explicit choice because a silent 10 GB ceiling is a worse surprise. `diagnose.sh` detects this variant and, because the container carries `sqlcmd`, queries the login's rights directly instead of inferring them from logs.

### Changed
- The deployment's `kb-scraper` now sets `Logging__LogLevel__Microsoft.AspNetCore=Warning`. The service ships no `appsettings.json`, so it fell back to the framework default of `Information` and logged three lines per HTTP request — with its health check polling every 15s, an idle scraper was the noisiest thing in `docker compose logs`. Set in the stack file rather than the SQL overlay, since the noise has nothing to do with which database is in use.
- **`diagnose.sh` is now served as a standalone file at `/deploy/diagnose.sh`**, so support can tell an operator `curl -fsSL https://<host>/deploy/diagnose.sh | bash` instead of walking them through downloading and unzipping the bundle. This reverses the earlier choice to ship it only inside the zip; the convenience won. The script is unauthenticated like the rest of `/deploy/`, and it reveals the same topology (container names, ports, env-var names) the deployment guide there already publishes. It reads and reports, never writes.
- **`diagnose.sh` now checks database *permissions*, not just reachability.** A TCP connect to SQL Server says nothing about whether the login can work, and SQL Server refuses in specific ways the API logs verbatim — so the script reads `bf-api`'s log for login failures (18456), unmapped-database errors (4060), denied SELECT/INSERT/CREATE TABLE grants, rejected TLS certificates and half-applied migrations, and names the fix for each. It cannot query SQL directly because the database is external and no host in the topology has a SQL client; when `sqlcmd` happens to be installed it does query the rights outright, and otherwise says plainly that it inferred them from logs. The API's `/health` per-check entries are now reported one line each instead of grepped for a single `Healthy`, so a failure names the subsystem.
- **Both Docker-deployment proxies are now nginx, configured by plain nginx files the operator edits.** One container per host does static serving, SPA fallback, the `/api` + `/hubs` reverse proxy, WebSocket upgrades and TLS. There are no templates and no environment-variable substitution: each host mounts a `nginx/` directory over `conf.d` holding `default.conf` (ours, replaced on upgrade) and `site.inc` (the operator's `server_name` and certificate paths, never touched by an upgrade). The directory is mounted rather than individual files because a single-file bind mount keeps resolving to the old inode after an editor rewrites the file, so an edit plus `nginx -s reload` appeared to do nothing. This replaces automatic certificate issuance, which needed inbound port 80 and public DNS at request time — often unavailable on ministry networks. `X-Forwarded-Proto` is preserved when nginx sits behind another proxy (`$fwd_proto`), so the API keeps generating `https://` URLs. The domain now appears both in `site.inc` and in `ALLOWED_ORIGINS`; `diagnose.sh` cross-checks them, since a mismatch loads the site but fails every API call on CORS. Production is unaffected — it serves the SPA as a static asset and never used this image stage. **Existing installs must upgrade with `docker compose up -d --remove-orphans`** to clear a retired `bf-caddy` container.

- The frontend image no longer generates nginx configuration at start: its entrypoint only writes the SPA's `env.js`, and `envsubst` is gone from the image. The baked config serves plain HTTP and is used only when the image runs without the deployment's mounts.
- The application stack's image tags are overridable with `IMAGE_TAG` (default `latest`), so a specific build can be pinned or a candidate image tested without moving `latest`.
- The deployment guide is now versioned (**1.1**) and documents only the current version, with a version-history section naming what changed. Older versions are not documented — operators on one are pointed at the upgrade section instead.
- Gemini chat requests now send a `generationConfig`: `maxOutputTokens` (default 512) caps over-long spoken answers, `temperature` (default 0.3) reduces topic drift versus the model's ~1.0 default, and `thinkingConfig.thinkingBudget` (default 0) disables gemini-2.5-flash "thinking" for lower voice latency. All three are tunable via the `Gemini` options section.
- The voice system prompt now instructs the model to answer only the user's most recent question, drop the previous topic when the subject changes, and keep spoken answers brief.
- Backend Azure Pipeline (`.azure/backend.yml`) now runs `dotnet test` on PRs targeting `main` and before every deploy; image build/deploy steps are skipped on PR runs (`Build.Reason != PullRequest`).
- **Frontend runtime configuration**: the SPA now reads `apiUrl` and `hubsUrl` from `window.__env` (served by `public/env.js`) before falling back to build-time `environment.ts`. This lets one image target any environment. Production (Static Web App) is unaffected — `window.__env` stays empty there, so baked values still apply.

### Added

- Per-turn backend telemetry: each conversational turn carries a `turnId` (minted by the agent at end-of-utterance, threaded through `/livekit/chat/turn`), and the backend emits a single `turn_completed` feed event at turn end with the full backend waterfall — total/TTFT latency, outcome, tool count, and an ordered `segments` list of Gemini inference spans and tool calls. All per-turn backend events (`llm_started`, `llm_first_token`, `kb_retrieved`, `llm_error`, `turn_completed`) now share the same `turnId` for grouping. Replaces the `llm_completed` event. The admin conversation feed shows `turn_completed` as a compact event row (outcome badge, TTFT/total timings, an info tooltip explaining each step) with an expand toggle that reveals the full per-turn latency waterfall (proportional Gemini-vs-tool segment bar); `turnId` is now exposed on telemetry event responses and the live hub feed.

Carries EOU/STT/LLM/TTS latencies plus LLM-TTFT and TTS-TTFB. The feed shows it as a compact row (with a step-by-step info tooltip) that expands to a pipeline waterfall, alongside the backend waterfall. Raw `metrics_collected` stays persisted (out of feed) for deep debugging.
